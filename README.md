# Telegram-бот «Делает ли ИИ домашку за вашего ребёнка?»

Лид-магнит проекта «ИИ и дети»: тест из 5 вопросов, Google Apps Script,
хранилище — лист «Ответы» в таблице «ИИ и дети — ответы теста».
Воронка: короткие видео → бот → трипваер.

| | |
| --- | --- |
| `src/Code.gs` | Рабочая версия 4.1, один файл — вставляется в редактор целиком |
| `src/appsscript.json` | Манифест проекта |
| `legacy/Code.v3.gs` | Архив версии 3 с багом, нужен тестам для воспроизведения |
| `test/` | Заглушки Apps Script и прогон логики в Node |
| `scripts/` | Развёртывание и проверка развёрнутого кода |

## Диагноз: почему бот замирал после второго вопроса

Причина найдена и **воспроизведена на стенде** (`node test/repro_freeze.js`).
Это не случайный сбой и не медленный Google — это гонка за состоянием диалога.

В версии 3 `startQuiz` вызывал `setState` дважды:

```js
setState(chatId, { step: 0, row: 0, answers: [], src: source });  // ①
askQuestion(chatId, 0, WELCOME);                                  // отправка вопроса
sheet.appendRow([...]);                                           // 1–3 секунды
setState(chatId, { step: 0, row: sheet.getLastRow(), ... });      // ② перезапись
```

Пока `appendRow` писал строку, пользователь успевал нажать кнопку первого
вопроса. Нажатие обрабатывается **отдельным, параллельным выполнением**
`doPost` — Apps Script их не сериализует, а блокировку в версии 3 убрали
ради скорости. Это выполнение ставило `step: 1` и отправляло второй вопрос.
Затем запоздавший `setState` ② записывал `step: 0` и `answers: []` —
**шаг откатывался назад, ответы стирались**.

Дальше всё детерминировано: кнопки второго вопроса несут `callback_data`
вида `"1:x"`, приходит проверка `step(1) !== state.step(0)` — и обработчик
делает тихий выход. Уходит только `answerCallbackQuery`: «часики» на кнопке
гаснут, и **больше не происходит ничего**. Строка в таблице остаётся
`начал` с пустыми ответами.

Вывод стенда на версии 3:

```
1. /start
   [во время appendRow] пользователь нажимает вариант первого вопроса
   состояние: {"step":0,"row":2,"answers":[],"src":"прямой"}   ← шаг откатан
2. пользователь нажимает вариант ВТОРОГО вопроса
   вызовов к Telegram: answerCallbackQuery
   третий вопрос пришёл: НЕТ — бот замер
4. дальнейшие нажатия по тем же кнопкам: answerCallbackQuery
```

### Вторая причина: дедупликация без блокировки

```js
if (cache.get(key)) return ok;
cache.put(key, '1', 21600);
```

Проверка и отметка — два отдельных действия. Telegram присылает повтор
недоставленного апдейта через 3 секунды, и если первое выполнение ещё идёт,
оба проходят проверку: строка и вопрос дублируются. Ломается это ровно в
медленном случае, то есть именно тогда, когда и нужно защищать.

Уточнение к более ранней версии этого разбора: интервалы между строками в
таблице (3, 5, 7, 10, 18, 34, 67 секунд, далее плато 1–2 минуты) — подпись
повторной доставки вебхука Telegram. Дедупликация в версии 3 уже была, но
из-за гонки выше она защищает не всегда.

### Третья причина: повторный /start плодил строки

Условие возобновления было `state.step > 0`, поэтому `/start` на нулевом
шаге проваливался в ветку создания и делал `appendRow` заново. Человек,
у которого бот замер, жал `/start` — и получал новую строку каждый раз.

## Что исправлено в версии 4

| Было | Стало |
| --- | --- |
| `setState` дважды, второй после записи в лист | Номер строки хранится отдельно от состояния диалога (свойство `r<chatId>`) и перезаписать шаг не может |
| Проверка и отметка `update_id` без блокировки | Переход состояния под `LockService`, но блокировка держится только на операциях с кэшем — десятки миллисекунд |
| Блокировка в версии 2 держала сеть и таблицу | Работа разделена: `planUpdate_` под блокировкой, `runPlan_` (сеть, лист) — без неё |
| Шаг сдвигался до отправки вопроса | Если вопрос не ушёл, шаг откатывается и приходит подсказка: диалог не замирает |
| Возобновление только при `step > 0` | `/start` возобновляет с любого шага, строка одна на `chat_id` |
| `appendRow` + `getLastRow()` | Номер строки после вставки ищется по `chat_id`: при одновременной вставке `getLastRow()` вернёт чужую строку |
| В лист писался только последний ответ | На финише пишутся все пять: потерянная по ходу запись восстанавливается |
| `writeAnswer` молча выходил при `row = 0` | Номер строки восстанавливается поиском, в крайнем случае строка создаётся заново |
| Вебхук без секрета | Секрет в query-строке (`?s=…`), проверяется в `doPost`; заголовки в Apps Script не читаются |
| `очиститьТаблицу` оставляла номера строк | Чистит и номера строк, и состояния диалогов |
| `WEBAPP_URL` только константой | Берётся из свойства `WEBAPP_URL`, константа — значение по умолчанию |
| Рассылка могла упасть по лимиту времени | Останавливается на 5-й минуте и пишет в журнал, где остановилась |

Тексты вопросов, результатов и ветка «младшая школа» перенесены из версии 3
без изменений. Токен по-прежнему только в свойствах скрипта.

## Автоматическое развёртывание

Разворачивать без копирования в браузер **можно**: у Apps Script есть
собственный API (`projects.updateContent`, `projects.versions.create`,
`projects.deployments.update`), а утилита `clasp` (проверено на 3.4.1) его
оборачивает. Главное для нас: при обновлении **существующего** развёртывания
адрес `/exec` не меняется, поэтому вебхук переставлять не нужно.

Ограничение, которое важно знать заранее: **Apps Script API не работает со
служебными аккаунтами** — нужен обычный вход пользователя. Поэтому `clasp
login` выполняется один раз руками, дальше всё автоматически.

### Настройка (один раз)

```
npm install                       # ставит clasp локально
npm run login                     # вход в аккаунт Google
```

Ещё нужно один раз включить Apps Script API на странице
`script.google.com/home/usersettings` — без этого `clasp push` откажет.

Затем два файла (оба в git не попадают):

```
cp .clasp.json.example .clasp.json       # scriptId: Настройки проекта → Идентификаторы
cp .env.deploy.example .env.deploy       # DEPLOYMENT_ID, WEBAPP_URL, WEBHOOK_SECRET
npm run deployments                      # покажет id существующих развёртываний
```

### Развёртывание

```
npm run deploy
```

Скрипт делает пять шагов и останавливается на первом же сбое:

1. прогоняет тесты — с красными тестами не разворачивает;
2. ставит в `src/Code.gs` отметку сборки: дата и хеш коммита;
3. `clasp push` — файлы уходят в проект;
4. создаёт новую версию и переводит на неё **существующее** развёртывание —
   адрес `/exec` сохраняется;
5. запрашивает у развёрнутого адреса его отметку сборки и сверяет с локальной.

Пятый шаг закрывает ровно ту ловушку, на которой мы стояли: сверяется не номер
версии, а отметка сборки, потому что одна и та же версия могла быть собрана из
разного кода. Только совпадение отметок означает, что развёрнут именно этот код.

| Команда | Что делает |
| --- | --- |
| `npm test` | Все тесты: логика бота и скрипты развёртывания |
| `npm run deploy` | Тесты → отправка → новая версия → проверка |
| `npm run verify` | Только проверка: что развёрнуто и что с вебхуком |
| `npm run deployments` | Список развёртываний с их id |
| `npm run logs` | Последние записи из журнала выполнений Apps Script |
| `npm run pull` | Забрать код из проекта, если правили в браузере |
| `npm run open` | Открыть редактор Apps Script |

Сборку в CI тоже можно, но там придётся хранить файл входа `.clasprc.json`
с токеном обновления как секрет. Для проекта на одного человека это лишнее.

## Почему бот остаётся на серверах Google

Локальный запуск на своём компьютере — плохой вариант именно для этой задачи,
и вот чем он расплачивается:

| | Apps Script | Компьютер дома |
| --- | --- | --- |
| Доступность | Круглосуточно, компьютер не нужен | Только когда компьютер включён и не спит |
| Из Китая | Бот живёт на серверах Google, к Telegram обращается оттуда | `api.telegram.org` в материковом Китае заблокирован: нужен постоянный VPN, его падение = молчащий бот |
| Вебхук | Есть готовый адрес `/exec` | Нужен публичный HTTPS-адрес либо переход на long polling |
| Стоимость | 0 ₽ | VPN и электричество, плюс ваше время на присмотр |
| Хранилище | Та же таблица, куда вы и так смотрите | Своя база, отчёты писать отдельно |

Трафик пойдёт с YouTube Shorts и VK Клипов на аудиторию России, то есть
заявки будут приходить круглые сутки и в основном не в ваши рабочие часы.
Бот, который отвечает только при включённом ноутбуке и живом VPN, будет терять
именно эти заявки.

При этом **разработка уже локальная**: код в git, тесты идут на вашем
компьютере (`npm test`), развёртывание одной командой. Копирование в браузер
больше не нужно — а это и было главным неудобством.

Если уходить с Apps Script понадобится (например, ради очередей, оплат или
своей базы), переезжать стоит не на домашний компьютер, а на небольшой сервер
вне Китая или на serverless-платформу. Скажите — подготовлю перенос.

## Где видно ошибки

Четыре места, от самого быстрого к самому подробному.

1. **Telegram — уведомления приходят сами.** Задайте свой `chat_id` в свойстве
   `ADMIN_CHAT_ID` (функция `включитьУведомления()` сделает это сама, если вы
   уже писали боту), и каждый сбой придёт сообщением: вид ошибки, версия кода,
   `chat_id`, что пришло, текст ошибки. Однотипные ошибки — не чаще одного
   сообщения в 10 минут, чтобы поток сбоев не стал потоком сообщений.
   Выключить: свойство `ALERTS` = `off`.
2. **Лист «Журнал» в той же таблице.** Строка на каждое обновление: время,
   итог, `update_id`, `chat_id`, что пришло, шаг, миллисекунды, подробности,
   версия кода. Открывать редактор не нужно.
3. **Журнал выполнений Apps Script** — в редакторе слева «Выполнения». Там
   всё, что попало в `console.log` и `console.error`, включая полный след
   исключения. Полезно, когда сломался сам журнал в таблице.
4. **Отчёт по адресу развёртывания** — откройте `/exec` в браузере. С ключом
   `?k=<WEBHOOK_SECRET>` там же состояние вебхука и последние 10 событий.

Ошибки доставки на стороне Telegram (скрипт до них не доходит) видны только
в `getWebhookInfo`: поля `pending_update_count` и `last_error_message`.
Их читает `проверка()`.

## Диагностика: бот молчит

Главная ловушка Apps Script: **функция, запущенная из редактора, работает на
последнем сохранённом коде, а вебхук вызывает развёрнутую версию.** Поэтому
`resetBot()` может отчитаться об успехе, пока Telegram продолжает звать старый
код. Версия 4.1 проверяет это сама.

### Шаг 1. Запустить `проверка()` (она же `checkHealth`)

Функция проходит цепочку по порядку и в конце печатает список проблем с
конкретными действиями:

1. токен — `getMe`, имя бота или причина отказа;
2. **развёрнутая версия** — скрипт обращается к собственному адресу и
   сравнивает версию с той, что в редакторе;
3. вебхук — адрес, очередь недоставленных, последняя ошибка доставки, наличие
   секрета в адресе;
4. триггеры — их при работе по вебхуку быть не должно;
5. таблица — листы, шапка, число строк;
6. последние 8 событий из журнала.

### Шаг 2. Посмотреть лист «Журнал»

Каждое обновление пишет строку: время, итог, `update_id`, `chat_id`, что
пришло, шаг, сколько миллисекунд занято, подробности. Это отвечает на главный
вопрос — дошло ли обновление до кода:

| Что в журнале после `/start` | Где ошибка |
| --- | --- |
| Строки нет вообще | Telegram не вызывает скрипт. Дело в развёртывании, адресе или вебхуке — логика бота тут ни при чём |
| `ОТБРОШЕН: СЕКРЕТ` | Вебхук поставлен без `?s=` или со старым секретом. `resetBot()`, либо свойство `ENFORCE_SECRET` = `off` |
| `ОШИБКА: НЕТ TOKEN` | Пустое свойство `TOKEN` |
| `ОШИБКА BOT API` | Telegram отклонил запрос, текст отказа в «Подробностях» |
| `ИСКЛЮЧЕНИЕ` | Сбой в коде, след в «Подробностях» |
| `ПУСТОЙ ЗАПРОС` / `БИТЫЙ JSON` | Адрес открыли не из Telegram |
| `пропущен` | Повторная доставка того же `update_id` — так и должно быть |
| `обработан` | Код отработал; если в Telegram ничего не пришло, смотрите «Подробности» и «Мс» |

### Шаг 3. Открыть адрес развёртывания в браузере

Отдаётся отчёт JSON с полем `версия_кода`. Если версия старая или вместо
отчёта что-то другое — **развёртывание не обновлено**, и это вся причина.
Полный отчёт с состоянием вебхука: `?k=<WEBHOOK_SECRET>`.

### Шаг 4. Команда `/diag` в самом боте

Отвечает версией кода, вашим `chat_id`, текущим шагом теста и номером строки.
Ответ на `/diag` доказывает, что обновления доходят до кода.

### Функции диагностики

| Функция | Что делает |
| --- | --- |
| `проверка()` / `checkHealth()` | Полная проверка цепочки с итогом |
| `webhookInfo()` | Сырой ответ `getWebhookInfo` |
| `tailLog(20)` | Последние записи журнала в консоль |
| `ping()` | Проверочное сообщение в `ADMIN_CHAT_ID` — проверяет путь «скрипт → Telegram» |
| `включитьУведомления()` | Настраивает адресата уведомлений об ошибках и сразу проверяет связь |
| `setLogLevel('all' \| 'errors' \| 'off')` | Уровень журнала. `all` — пока налаживаем, `errors` — в работе |
| `очиститьЖурнал()` | Чистит лист «Журнал» |
| `resetStuckDialogs()` | Сбрасывает зависшие диалоги |

Запись в журнал — это один `appendRow` на обновление, примерно треть секунды.
Когда бот заработает, поставьте `setLogLevel('errors')`: сбои по-прежнему
будут фиксироваться, а успешные шаги перестанут занимать время.

### Свойства скрипта

| Ключ | Назначение |
| --- | --- |
| `TOKEN` | Токен бота, обязательно |
| `WEBHOOK_SECRET` | Создаётся автоматически в `resetBot()` |
| `ENFORCE_SECRET` | `off` отключает проверку секрета, если она мешает |
| `WEBAPP_URL` | Адрес развёртывания, если отличается от константы в коде |
| `ADMIN_CHAT_ID` | Куда присылать уведомления об ошибках и `ping()`; свой `chat_id` покажет `/diag` |
| `ALERTS` | `off` выключает уведомления об ошибках в Telegram |
| `LOG_LEVEL` | `all`, `errors` или `off` |

## Порядок запуска вручную

Если разворачиваете через браузер, а не командой `npm run deploy`:

1. Ctrl+A в редакторе Apps Script, вставить `src/Code.gs` целиком. Сохранить.
2. **Развернуть → Управление развёртываниями → карандаш → Версия: Новая →
   Развернуть.** Без этого шага бот остаётся на старом коде.
3. Выполнить `resetBot()`. Функция сама создаст `WEBHOOK_SECRET`, поставит
   вебхук с `drop_pending_updates` и сверит развёрнутую версию с той, что в
   редакторе. Если она пишет «ВЕБХУК НЕ УСТАНОВЛЕН» или «отвечает версия…» —
   читайте её вывод, там названа причина.
4. Выполнить `проверка()` — полный отчёт о состоянии.
5. Выполнить `dedupeSheet()` — отчёт по дублям. Затем `dedupeSheet(true)`,
   чтобы склеить их в одну строку на человека.
6. В Telegram нажать `/start` и пройти тест до конца. Если тихо — `/diag`,
   затем лист «Журнал».

Если развёртывание создано заново и URL изменился, положите новый URL в
свойство `WEBAPP_URL` и снова выполните `resetBot()`.

## Тесты

```
npm test                          # всё: 55 проверок логики + 10 на скрипты развёртывания
node test/run_tests.js            # логика версии 4 и диагностика
node test/test_deploy_tools.mjs   # скрипты развёртывания на локальном сервере
node test/repro_freeze.js         # воспроизведение зависания версии 3
```

Среди проверок — сам баг: нажатие кнопки во время записи строки в лист
должно оставить тест живым и довести его до статуса «завершил»; повторная
доставка одного `update_id` 54 раза должна дать одну строку и один вопрос;
блокировка не должна удерживаться во время обращений к сети и таблице.

`selfTest()` внутри редактора проверяет все 64 комбинации первых трёх
ответов: у каждой должны быть непустые сегмент, зона и текст результата.

## Логика результата

Сегмент — по второму вопросу: Пользователь, Контролёр, Смешанный, Новичок.
Зона — по третьему: «прошу объяснить своими словами» → зелёная, «сверяю
сам» → жёлтая, остальное → красная. Первый класс отдельной веткой:
рекомендации Минпросвещения от 12.09.2026 не предполагают ИИ в 1–4 классах.
