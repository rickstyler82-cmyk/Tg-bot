# Telegram-бот «ИИ и дети» — лид-магнит (тест из 5 вопросов)

Google Apps Script + Google Sheets. Воронка: короткие видео → бот → трипваер.
Таблица ответов: «ИИ и дети — ответы теста».

## Диагноз: почему бот дублировал вопросы и «долго думал»

Исходный скрипт лежит контейнерным Apps Script внутри таблицы, и его текст
через Drive API недоступен, поэтому причина установлена по данным таблицы.
Улика однозначная — интервалы между строками за 15.09.2026:

```
14:41:54  14:41:57 (+3s)  14:42:02 (+5s)  14:42:09 (+7s)  14:42:19 (+10s)
14:42:37 (+18s)  14:43:11 (+34s)  14:44:18 (+67s)  далее 74 минуты по 65–120 s
```

3 → 5 → 7 → 10 → 18 → 34 → 67 → плато 1–2 минуты — это не поведение человека,
это алгоритм повторной доставки вебхука Telegram. Telegram повторяет один и тот
же `update`, пока endpoint не ответит `200 OK`, и повторяет неограниченно долго.
54 строки с одинаковым содержимым («начал», пустые ответы) — это 54 повторные
доставки одного нажатия `/start`.

Отсюда обе жалобы, у них одна причина:

| Симптом | Механизм |
| --- | --- |
| Дублирует вопросы | Каждая повторная доставка заново проходит обработчик и снова отправляет вопрос |
| Долго думает | Ответ на нажатие приходит не с первой доставки, а с той, которая случайно успела; спиннер на кнопке не гасился |
| 54 строки на одного человека | На каждый апдейт делался `appendRow` вместо обновления строки этого `chat_id` |
| Тест начинается заново | Шаг восстанавливался из таблицы, а в таблице появилась новая пустая строка |

Что в Apps Script возвращает не-200: любое необработанное исключение в `doPost`
(ошибка Bot API, `undefined` в поле апдейта, таймаут, превышение квоты) и
превышение лимита времени выполнения.

## Что исправлено

1. **`doPost` всегда возвращает `200 OK`** (`src/30_Bot.gs`). Весь обработчик в
   `try/catch`, ошибка уходит в лог. Это обрывает цикл повторных доставок.
2. **Идемпотентность по `update_id`** — `seenUpdate_()` через `CacheService`,
   TTL 6 часов. Даже если Telegram доставит апдейт повторно, он отбрасывается.
3. **Проверка и отметка `update_id` под `LockService`** — иначе две
   одновременные доставки успевают проскочить проверку обе.
4. **Одна строка на `chat_id`** — `rowUpsert_()` вместо `appendRow`. Номер
   строки кэшируется в `r_<chatId>`, поэтому нажатие кнопки не читает лист
   целиком (это же убирает деградацию по мере роста таблицы).
5. **Состояние диалога в свойствах скрипта**, а не в таблице (`st_<chatId>`:
   шаг, ответы, id сообщения). Лишняя строка в листе больше не сбрасывает тест.
6. **Защита от старых кнопок** — в `callback_data` зашит номер шага
   (`a|<шаг>|<индекс>`). Нажатие на уже отвеченный вопрос подтверждается
   всплывающей подсказкой и не двигает шаг: повторный вопрос не приходит.
7. **Спиннер гасится первым действием** — `answerCallbackQuery` уходит вместе с
   правкой сообщения одним `fetchAll`. Одно нажатие = 2 раундтрипа максимум,
   `/start` = 1 (проверено тестами 8 и 14).
8. **Отвеченный вопрос правится на месте** (`editMessageText`), новых сообщений
   не появляется; клавиатура снимается, чтобы по ней нельзя было нажать снова.
9. **Запись в лист после отправки сообщений** — лист не стоит на пути к ответу.
10. **Секрет вебхука** в query-строке (`?s=…`): заголовки в Apps Script не
    читаются, поэтому проверка сделана через `e.parameter.s`.
11. **`drop_pending_updates: true`** при установке вебхука — иначе после починки
    бот сразу отработает всю накопленную очередь и снова насыплет дублей.
12. **Свободный текст и `/start` больше не плодят строк**, `/help` и `/restart`
    добавлены.

Токен в коде не хранится: `BOT_TOKEN`, `WEBHOOK_SECRET`, `WEBAPP_URL`,
`TRIPWIRE_URL` живут в Script Properties.

## Порядок развёртывания

1. Открыть таблицу → **Расширения → Apps Script**.
2. Заменить содержимое проекта файлами из `src/` (имена задают порядок
   конкатенации). Манифест — `src/appsscript.json` (включить показ манифеста в
   настройках проекта).
3. **Project Settings → Script properties**: добавить `BOT_TOKEN`. Запустить
   `initProperties()` — он сгенерирует `WEBHOOK_SECRET`.
4. **Deploy → New deployment → Web app**: Execute as **Me**, Who has access
   **Anyone**. Скопировать URL `…/exec` в свойство `WEBAPP_URL`.
5. Запустить `installWebhook()`.
6. Запустить `webhookInfo()` и проверить: `pending_update_count: 0`,
   `last_error_message` отсутствует. Это главный индикатор здоровья бота.
7. Запустить `listTriggers()`. Триггеров быть не должно: триггер по времени с
   `getUpdates` рядом с вебхуком обрабатывает апдейты вторично. Если есть —
   `removeAllTriggers()`.
8. Разобрать уже накопленные дубли: `dedupeSheet()` — отчёт без изменений,
   затем `dedupeSheet(true)` — склеить. Непустые значения из дублей
   поднимаются в оставшуюся строку, свежее значение побеждает.

После любой правки кода нужен **новый деплой** (Deploy → Manage deployments →
Edit → New version), иначе вебхук продолжит дергать старую версию.

## Тесты

```
node test/run_tests.js
```

14 проверок, среди них воспроизведение исходного бага: 54 повторные доставки
одного `update_id` должны давать одну строку и один отправленный вопрос.
`selfTest()` внутри редактора Apps Script проверяет расчёт зон и сегментов
без обращения к сети и таблице.

## Логика результата

Сегмент — по ответу «кто пользуется»: А (родитель-пользователь),
Б (родитель-контролёр), А+Б, В (на входе, застрял на «какой чат скачать»).

Зона считается по общей боли «никто не умеет проверять», а не по «ребёнок
списывает домашку»: домашку могут отменить, а неумение проверять останется.
Тон результата — без вины и без паники, от преимущества.
